# 五要素核验规则（verification-rules）

依据支付宝 AI 付 Machine Pay（A2M）公开文档，`verify` 接口返回 `active=true` 只代表平台侧已收款，
业务侧还必须自行完成以下校验，全部通过才能发货。

| # | 校验项 | 字段 | 违规码 | 不通过的后果 |
|---|---|---|---|---|
| 1 | 凭证有效 | `active` | OFG_1001 | 拒绝交付 |
| 2 | 金额一致 | 凭证 `amount` = 订单 `amount` | OFG_1002 | 拒绝交付，疑似篡改 |
| 3 | 订单号一致 | `out_trade_no` | OFG_1003 | 拒绝交付 |
| 4 | 资源一致 | `resource_id` | OFG_1004 | 防止 A 单领 B 货 |
| 5 | 交易号未使用 | `trade_no` 全局唯一 | OFG_1005 | 判定重放，拒绝交付 |
| 附 | 订单未被他单履约 | 同订单其他 `trade_no` | OFG_1008 | 拒绝交付 |
| 弱 | 会话归属一致 | `client_session` | OFG_3003 | 仅风险提示，不单独阻断 |

## 为什么必须防重放

Agent 遇到网络超时会自动重试，HTTP 客户端也可能重放请求。若只校验"凭证有效"，
同一笔已支付凭证可以被反复提交，导致一次付款多次发货。OFG 以 `trade_no` 为幂等键落库，
并以 `fulfillment_id` 保证核销接口本身的幂等：重复调用返回首次结果，不产生第二条权益流水。

## 金额处理

所有金额以字符串入参、`Decimal("0.01")` 量化后比较，禁止使用 float，
从根上避免 `0.1 + 0.2 != 0.3` 造成的金额误判。
