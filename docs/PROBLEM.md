# 真问题定义：AI 产品商业化的最后一公里，是「收款之后的可信履约」

> 本文基于 PAYATHON 2026 全量 664 件参赛作品、337 条社区问答、418 篇参赛手记与官方产品文档归纳，
> 先定义真问题，再给出 Skill 层与 Agent 层两个互补方案。

## 1. 现象：大家都在「能收款」，没人真正解决「敢交付」

调研三类一手材料后，问题并不在"AI 功能不够强"，而在交易闭环：

1. **社区问答 337 条，卡点高度集中在支付后链路**：付款后订单状态查不到、扫码触发风控报错、密钥配置失败、回调与退款缺失、个人收款限额与合规、活动结束后通道是否保留、Payment-Proof 验证不过。真正问"怎么发起一笔支付"的反而很少。
2. **664 件作品同质化，支付大多停在"贴一个收款码/单次解锁"**：普遍缺少幂等控制、凭证防重放、权益核销、日结对账与退款判定。官方评选四维度中，"支付集成度"明确要求"从发现、使用到付款、交付整条链路跑通"，而不是拉起收银台就算完成。
3. **Agent/Machine 赛道 83 件作品多为概念演示**：真正实现官方 `402 Payment Required → amtPaymentLink → Payment-Proof → verify → 防重放交付` 完整时序的极少。机器买家需要的是机器可读目录、标准账单、可核验回执，而不是一个演示页面。

## 2. 真问题（一句话）

> **当一次 AI 交易发生后，"钱是否真的对应了一次且仅一次、可追溯、可退款的正确交付"，目前没有被低成本地保证——对人如此，对自主交易的 Agent 更是如此。**

拆成四个必须同时成立的子问题：

- **一致性**：支付凭证里的金额、商户订单号、资源 ID，必须与本次交付严格匹配（官方 verify 要求校验 `active / amount / out_trade_no / resource_id`）。
- **幂等与防重放**：同一笔支付（`trade_no`）只能履约一次，网络重试、Agent 重放、并发请求都不能重复发货或重复扣款。
- **权益与对账**：一次性买断、次数包、时长包需要可核销、可盘点；本地订单要能和平台账单逐日核对，差异可定位。
- **责任可追溯**：预下单、支付、验证、交付、退款每一步留痕，出现纠纷能回放；这正是平台 APASS "可信存证、意图安全、权责判定"的落点。

## 3. 三方需求对齐

| 角色 | 核心诉求 | 现状痛点 |
|---|---|---|
| 卖家（独立开发者/小团队） | 低成本接入、自动核销与对账、防薅羊毛、合规可申诉 | 没有精力自建交易系统，常把密钥放前端、缺幂等与退款流程 |
| 买家（人或 Agent） | 报价透明、付了必交付、凭证可验证、可退款、不重复扣款 | 付款后状态不明、自动续费焦虑、Agent 无法机器读懂账单 |
| 平台（支付宝 AI 付） | 真实交易、可核验用量、风控与责任追溯、繁荣供给 | 需要可复用的履约范式，把"真实付费"标准沉淀给大量长尾开发者 |

结论：缺的不是收银台，而是一层**可复用的交易履约信任层（Fulfillment Trust Layer）**。

## 4. 两个互补方案（同一真问题，两个视角）

| | 方案 A：Skill 层 | 方案 B：Agent 层 |
|---|---|---|
| 名称 | `order-fulfillment-guard` 履约核验技能 | `aipay-402-gateway` 智能体按量付费履约网关 |
| 参赛赛道 | Skill Pay（技能商品，买断/按次） | Machine Pay + Agent Pay（402 按量、Agent 自主交易） |
| 使用者 | 开发者、运营、客服（人在 Agent/IDE 里调用） | AI Agent / 机器客户端（无人为干预自动交易） |
| 解决面 | 事后核验、核销、对账、退款初判、风控信号 | 事前报价、事中 402 收款与凭证验证、事中自动履约 |
| 交付物 | 标准 AI Skill 包（SKILL.md + 可执行脚本 + 规则库） | 可部署 FastAPI 服务 + 客户端 SDK + Docker + 测试 |
| 无密钥可跑 | 内置样例数据与离线规则引擎 | 内置 Mock 支付提供方，一键切换真实支付宝接口 |

两者共用同一套协议词汇（`out_trade_no / trade_no / resource_id / Payment-Proof`）与同一套五要素核验规则：
Skill 是"人侧的履约裁判"，Gateway 是"机器侧的自动履约流水线"，合起来构成完整的可信履约闭环参考实现。

## 5. 边界与诚实声明

- 仓库内置的是 **Mock 支付提供方**，可在没有商户密钥的情况下完整跑通协议时序；真实接入需在配置中填入 AppId、RSA2 密钥与 `service_id`，代码已预留 `AlipayAipayProvider` 适配骨架，字段对齐官方 `precreate / verify` 接口，但不替代官方 SDK 与签约流程。
- 金额、接口名、响应头均依据支付宝 AI 付公开文档（Machine Pay A2M 方案）编写；上线前以官方最新文档为准。
